# Repository Guidelines

## Project Overview

**TOOLCODE** (`toolcode`, v0.0.1) is a terminal coding agent with a bring-your-own-model-provider
architecture. An Ink/React TUI drives an agent loop that streams completions from a pluggable
provider, executes tool calls against a sandboxed workspace, and renders the result live.

- **Zero-runtime-dependency core** — only `ink` and `react` are runtime deps; HTTP, SSE parsing, and
  all file access use Node built-ins (`node:fs`, `node:path`, `node:url`).
- **Provider-agnostic** — OpenRouter ships built-in; Ollama / llama.cpp / anything OpenAI-compatible
  arrives via drop-in plugins (see `PLUGINS.md`).
- **Demo fallback** — with no API key set, the app transparently streams from `src/providers/demo.ts`
  instead of failing, so the UI is always explorable.

## Architecture & Data Flow

```
CLI flags (src/cli.tsx)
  └─> loadPlugins()                     src/plugins/loader.ts
  └─> render(<App plugins=... />)       src/ui/App.tsx
        └─> useChat()                   src/ui/hooks/useChat.ts   (state + 32ms batched stream flush)
              └─> runAgent()            src/core/agent.ts        (async generator)
                    ├─> systemPrompt()  src/core/prompts.ts
                    ├─> provider.stream() AsyncGenerator<ProviderEvent>
                    └─> tool.run(args, ctx)  src/tools/registry.ts
```

**One turn of the agent loop** (`runAgent`, `src/core/agent.ts`):

1. User input is formatted by `userPrompt(kind, input)` and appended to `ChatMessage[]` history.
2. Tools are filtered by `toolsFor(isReadOnlyTurn(kind))`. `plan` / `improve` / `judge` turns get
   **only** `readOnly: true` tools.
3. `systemPrompt()` is rebuilt with workspace root, platform, tool docs, and a file snapshot from
   `listFiles(cwd, 400)`.
4. `provider.stream()` yields `{type: 'text', delta}` incrementally, plus complete
   `{type: 'tool_call', call}` objects (SSE fragments are buffered by index until whole).
5. Tool calls run **sequentially**; each emits `tool_start` → `tool_end` `StreamEvent`s, and the
   result is appended as a `{role: 'tool', tool_call_id, content}` message.
6. Loop exits on: no tool calls, `MAX_STEPS = 40`, abort, or provider error.

**Key invariants**

- `src/tools/registry.ts` and `src/providers/registry.ts` hold **module-scoped mutable arrays**.
  Registration mutates global runtime state; both export `unregister*` for test cleanup.
- The UI **never** calls tools. It only consumes `StreamEvent`s and reads back `session.todos`.
  Tools reach the UI by mutating `ctx.session.todos` or awaiting `ctx.ask`.
- Completed turns render inside Ink's `<Static>` so they scroll back permanently. Redrawing
  history after a clear requires bumping the `epoch` counter in `src/ui/App.tsx`.

## Development Commands

```bash
npm install                  # npm is the package manager (package-lock.json v3)
npm run dev                  # run from source: tsx src/cli.tsx
npm run build                # tsc: src/ -> dist/ (+ .d.ts, .js.map)
npm run typecheck            # tsc --noEmit
npm test                     # builds first, then: node --test test/*.test.mjs
npm run smoke                # builds first, then headless UI smoke (default 'main' scenario)

# Single test file (build is mandatory — tests import ../dist/*)
npm run build && node --test test/todos.test.mjs

# Named smoke scenario; first arg is terminal width
node scripts/ui-smoke.mjs 90 agent      # main | plugins | agent | agent-skip | overlays | edge | ascii | error

# Try the bundled example plugins
node dist/cli.js --plugin plugins
```

**Absent tooling — do not invent commands:** there is **no linter** (no ESLint/Biome) and **no
formatter** (no Prettier) configured. `npm run lint` and `npm run format` do not exist. Match
surrounding style by hand.

## Code Conventions & Common Patterns

- **Formatting**: tab indentation, single quotes, semicolons, no space inside braces
  (`import {render} from 'ink'`), 2-space continuation for object literals, JSDoc `/** */` on
  exported functions, inline `//` notes explaining *why*.
- **ESM only.** `"type": "module"` + `moduleResolution: NodeNext` means **every relative import in
  `src/` must end in `.js`** — `import {x} from './types.js'`, even though the file is `.ts`. Use the
  `node:` prefix for built-ins.
- **naming**: `camelCase` files/functions for non-components; PascalCase `.tsx` files in
  `src/ui/components/` exporting one same-named function; `interface Props` declared directly above
  the component; `SCREAMING_SNAKE` for module constants (`MAX_STEPS`, `MAX_QUESTIONS`).
- **Error handling**: throw plain `Error` for validation failures. The agent loop catches tool
  throws and converts them to `{status: 'error', summary, content: 'Error: ' + message}` — do **not**
  hand-roll error objects. For cancellation use `AbortError` / `isAbortError()` from
  `src/core/abort.ts`; aborted messages get status `interrupted`, not `error`.
- **Async style**: `async` functions and `async function*` generators throughout; the agent loop and
  providers are async generators, never callbacks or event emitters.
- **Dependency injection**: capabilities reach tools through the `ToolContext` object
  (`{cwd, signal, session, ask, resolvePath}`) — not module imports. This is what makes tools
  testable and plugins sandboxable. Keep it that way.
- **State management**: plain React `useState` / `useRef` / `useCallback` / `useEffect`. No Redux,
  Zustand, or context beyond the single `ThemeProvider`. Streaming updates are batched on a
  `FLUSH_MS = 32` timer in `useChat.ts` — extend that path rather than adding per-token renders.
- **Theming**: never hardcode colors or glyphs. Use
  `const {colors, symbols, borderStyle} = useTheme()`; it already switches Unicode ↔ ASCII for
  `--ascii`. For width-sensitive text use `useTerminalWidth()` and `truncateMiddle()`.

### Adding a tool

1. Create `src/tools/<name>.ts` exporting a `Tool` (`src/tools/types.ts`): `name`, `label`,
   `description`, `parameters: JsonSchema`, `readOnly`, `describe(args)`, `async run(args, ctx)`.
2. Always resolve paths through `resolveInWorkspace(cwd, file)` — it throws on `..` escapes, on
   absolute paths outside cwd, and on targeting the workspace root itself.
3. Return `ToolResult` `{status, summary, output?, content}`; `summary` is the one-line UI label,
   `content` is what the model sees.
4. Register it in the array in `src/tools/registry.ts`. Set `readOnly: true` if it should remain
   available in plan mode.

### Adding a provider or plugin

Providers implement `stream(request): AsyncGenerator<ProviderEvent>`. Plugins are plain JS ESM
files in `~/.toolcode/plugins/` (or via `--plugin`) whose default export is a `PluginDefinition`
`{name?, tools?, providers?, commands?}` — object or (async) factory. Plugins contribute tools,
providers and slash commands (a command's `name` is lowercased and typed as `/name`), but never UI
components. Loading is all-or-nothing per file: one bad name or id
rejects the whole plugin. Providers declaring `baseUrl` are auto-wired to `openAICompatibleStream`.
Plugin tools should guard `if (ctx.ask)` — it is undefined outside the interactive TUI.

## Runtime & Tooling Preferences

- **Runtime**: Node.js `>= 20` (`engines`). No Bun, Deno, or browser support.
- **Package manager**: **npm** — commit `package-lock.json`; do not introduce yarn/pnpm/bun lockfiles.
- **Language**: TypeScript `^7`, `strict: true`, `target ES2022`, `jsx: react-jsx` (React 19
  automatic runtime, so no `import React` needed).
- **Dev runner**: `tsx` for `npm run dev`; no watch mode is configured.
- **tsconfig scope**: `include: ["src"]` only. `test/` and `scripts/` are plain JS and are **not**
  typechecked — keep them syntactically valid by hand.
- **Dist is derived**: `dist/` is gitignored but tests and the `bin` entry read from it. Never
  commit or hand-edit `dist/`.
- Plugins run arbitrary code with user permissions. TOOLCODE deliberately never auto-loads plugins
  from the project CWD — keep that property when touching `src/plugins/loader.ts`.

## Testing & QA

- **Runner**: Node's built-in `node:test` with `node:assert/strict`. No Jest/Vitest/Mocha.
- **Language**: tests are plain ESM JS named `test/*.test.mjs` — not TypeScript.
- **Critical**: tests import from `../dist/…`, never from `src/`. **Always rebuild** before testing,
  or you will be asserting against stale output. `npm test` does this for you; a bare
  `node --test test/foo.test.mjs` will not.
- **Helpers** (`test/helpers.mjs`): `tempDir()` → `{dir, cleanup}` (always call `cleanup()` in a
  `finally`); `scriptedProvider(steps)` → `{requests, provider}` for fake model responses;
  `runTurn({provider, cwd, ...})` → drains `runAgent` and collects events plus `toolEnds`.
- **Fixture**: `test/fixtures/scripted-provider.mjs` is a real plugin file (`id: 'scripted'`) that
  asks two questions, writes todos, then echoes answers — used by the UI smoke tests.
- **Covered**: filesystem tools and path-traversal rejection, plan-mode restrictions, the todo DAG
  (cycles, blocking, cross-turn state), plugin loading and failure isolation, and the `ask` tool.
- **UI has no unit tests.** The 15 components and both hooks are verified only by
  `scripts/ui-smoke.mjs`, which renders `<App>` against mock `EventEmitter` stdin/stdout and prints
  frame blocks; `test/ui.test.mjs` shells out to it and regex-matches stdout. To change UI, run
  `npm run smoke` and check the relevant scenario, and add a scenario there rather than a component
  test.
- **No coverage tooling** is configured. Add a case when a change introduces a plausible bug in an
  existing behavior; do not add tests that merely restate the implementation.
